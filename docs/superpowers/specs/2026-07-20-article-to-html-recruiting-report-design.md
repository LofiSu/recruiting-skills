# Article-to-HTML Recruiting Report Design

## Goal

Replace the current generic card UI in every generated `report.html` with a
Chinese recruiting-intelligence dossier based on the `article-to-html` design
system. Preserve the existing single-file output contract, complete author
coverage, auditability, security controls, and offline operation.

The report is optimized for a Chinese-speaking recruiter who needs to scan
all paper authors, find the strongest public professional contact route, and
inspect the evidence behind every identity and contact claim.

## Confirmed product decisions

- Modify the HTML generator so every future report uses the new design.
- Use the selected “Recruiting intelligence dossier” layout.
- Render interface labels and explanatory copy in Chinese.
- Keep author names, paper titles, affiliations, evidence values, source
  names, URLs, and other collected data in their original language.
- Collapse full evidence, contact provenance, and source attempts by default.
- Keep all authors present in the server-rendered document even when
  JavaScript is unavailable.

## Approaches considered

### A. Editorial long-form paper

Render the paper and every author as one continuous numbered article. This is
the closest match to the stock `article-to-html` template, but it becomes
slow to scan when a paper has many authors.

### B. Recruiting intelligence dossier

Combine a sticky author index with sequential author dossiers. The index
provides fast navigation and compact status cues; each dossier prioritizes
the best public contact route while retaining expandable audit details. This
is the selected approach because it balances recruiting speed with complete
evidence.

### C. Analyst roster

Lead with a dense comparison table and open a selected author below it. This
is efficient for very large author lists but weakens the paper-like reading
experience and depends more heavily on interactive state.

## Visual system

The report adopts the `article-to-html` visual invariants:

- `--paper: #f7f7f5` and `--ink: #1a1a1a`;
- serif body text and monospace metadata;
- restrained red-brown accent color;
- numbered section prefixes;
- thin rules and flat paper surfaces instead of generic rounded card grids;
- no external fonts, stylesheets, scripts, images, or CDNs;
- no “generated by AI” watermark.

The interface uses no emoji icons. Uppercase or compact monospace labels,
status marks, rules, and typographic hierarchy provide the visual vocabulary.

## Page structure

### Document header

The header contains:

- report type;
- original paper title;
- arXiv identifier and source URL;
- original categories and submission metadata;
- generated timestamp;
- original abstract;
- a deterministic Chinese TL;DR.

The TL;DR is computed from normalized run data and reports:

- total authors;
- authors with public professional contact routes;
- confirmed, ambiguous, and not-found identity counts;
- unavailable-source count.

It does not use an LLM or invent a narrative assessment.

### Recruiting workspace

Desktop layout uses two columns:

- a sticky author index on the left;
- sequential author dossiers on the right.

Each index entry contains paper order, original author name, contact status,
and confidence. Its anchor targets the matching server-rendered dossier.
Clicking an entry scrolls to that author. Scroll position highlights the
current index entry when JavaScript is available.

On narrow screens, the author index becomes a horizontal, scrollable
navigation row above the dossiers. The report remains readable at 320px
without horizontal page overflow.

### Author dossier

Each author dossier displays, in priority order:

1. paper order and original author name;
2. original affiliation;
3. identity state, confidence, and contact status;
4. a prominent “best public contact route” block;
5. verified public professional email or contact form when present;
6. Homepage, GitHub, OpenReview, and ORCID profile routes;
7. Google Scholar, LinkedIn, Maimai, and other locator-only links;
8. identity reasons;
9. collapsed contact-point provenance;
10. collapsed complete evidence;
11. collapsed per-author source attempts.

If no verified public professional contact exists, the dossier explicitly
states that outcome and retains locator links and source status. Ambiguous
identities, robots restrictions, rate limits, unavailable sources, and
not-found results remain visible.

### Compliance section

The final numbered section explains the public-professional collection
boundary and identifies locator-only platforms. It states that no login,
CAPTCHA, paywall, robots exclusion, or other access control was bypassed.

## Interaction design

The document works without JavaScript. JavaScript only enhances already
rendered content:

- filter the author dossiers and matching index entries by name;
- filter by contact status;
- highlight the current author while scrolling;
- expand or collapse all audit sections;
- return to the top of the document.

Filters never mutate, remove, or rewrite source data. Clearing filters
restores the original paper order. Native `<details>` elements provide
keyboard-accessible disclosure controls.

## Rendering architecture

The paper resolver, source adapters, identity matcher, contact aggregator,
models, and normalized candidate records remain unchanged.

`researcher_recruiting/exporters.py` continues to:

1. create candidate records;
2. create author-scoped source-attempt records;
3. redact and normalize the complete render payload;
4. render one self-contained HTML string;
5. atomically publish a timestamped directory containing only
   `report.html`.

The implementation refactors the renderer into focused helpers where useful:

- deterministic report summary;
- author-index entry;
- best-contact route;
- profile and locator link groups;
- author dossier;
- embedded style and enhancement script.

The public `write_artifacts` interface and `ARTIFACT_NAMES =
("report.html",)` contract remain unchanged.

## Security and privacy

Existing security boundaries remain mandatory:

- HTML-escape all paper, author, evidence, metadata, source, and error text;
- allow only valid `http`, `https`, and field-appropriate `mailto` links;
- omit malformed or unsafe evidence and contact URLs;
- redact bearer credentials, tokens, API keys, and client secrets;
- omit opaque paper-email provenance;
- do not embed untrusted evidence as markup or executable code;
- do not load remote assets or analytics.

The redesign must reuse the existing safe-link and redaction helpers instead
of introducing parallel sanitization logic.

## Failure behavior

Partial runs still produce a complete report. A failed optional source never
removes its author. A filesystem error preserves the current atomic-write
behavior and leaves no partially published run directory.

Every author remains represented exactly once and in paper order, including
authors whose identity is ambiguous or whose contacts were not found.

## Test strategy

Implementation follows test-driven development.

New failing tests first define the visual and structural contract:

- Chinese interface labels are present while original content is unchanged;
- paper and ink design tokens match the `article-to-html` invariants;
- a deterministic TL;DR contains the expected run counts;
- every author appears in both the index and one dossier;
- index links target stable author anchors;
- numbered document sections are present;
- audit sections use closed `<details>` elements by default;
- the best public contact route prefers verified direct contact;
- filtering controls and progressive-enhancement hooks are present;
- the mobile layout rule is included.

Existing tests continue to prove:

- the run directory contains only self-contained `report.html`;
- all authors remain in paper order;
- duplicate names remain author-ID scoped;
- contact provenance, evidence, and source attempts remain complete;
- unsafe links and markup cannot execute;
- secrets and opaque paper-email provenance are absent;
- malformed values do not prevent publication.

Verification includes:

1. targeted exporter tests;
2. the complete non-network test suite;
3. Python compilation;
4. a fresh `arXiv:2601.21998` run;
5. browser inspection at desktop and mobile widths;
6. interaction and console-error checks;
7. confirmation that all expected authors are present.

## Documentation and example output

Documentation continues to describe `report.html` as the only output
artifact. The existing `arXiv:2601.21998` example is regenerated in
`outputs/` for user review, but generated outputs remain outside the source
commit unless explicitly requested.
